# Available Computing 个人版 V1 升级执行方案

## 1. 产品边界

V1 面向个人自托管使用：聚合个人持有的免费 AI 厂商凭证，对本机或个人项目提供统一代理。

优先目标：

1. 免费模型更多：降低标准 OpenAI 兼容厂商的接入成本。
2. 可用性判断可信：每个状态都有真实调用证据和明确新鲜度。
3. 代理稳定：限流后自动降级，并能区分模型故障和厂商凭证故障。
4. API 实用：保留 OpenAI 兼容，并逐步覆盖 chat、embedding、rerank 和 image。

V1 不建设多租户计费、复杂审批流、多节点探测和完整消息中心。继续采用单容器、SQLite、单机密钥存储。

## 2. 状态语义

### Model

- `last_checked_at`：最近一次调用尝试，无论成功或失败。
- `last_verified_at`：最近一次成功完成真实请求的时间；目录查询 `/models` 不算验证。
- `verification_method`：产生最近成功验证的方式。
- `staleness_threshold_days`：超过该时间未成功验证则显示“待确认”，默认 7 天。
- `free_expires_at`：限时免费能力的已知到期时间，与 `free_type` 分离。

历史数据不得用迁移时间伪造验证。只能从 `last_success_at` 或成功的 `HealthRecord` 回填；没有证据时保持 `NULL`。

### Channel

- `active`：凭证可用。
- `key_invalid`：上游明确拒绝凭证。
- `key_expired`：已知凭证有效期已经结束。
- `suspended`：账户级错误或连续探测异常。
- `unconfigured`：保留给后续候选厂商流程。

模型失败不能直接推导 Channel 失效；只有明确的账户级信号才能改变 Channel 状态。

### HealthRecord

`HealthRecord` 是验证证据，记录验证方式、HTTP 状态、检查批次、失败原因和当次限流快照。Model 和 Channel 只保存便于查询的最新状态快照。

## 3. 实施阶段

### 阶段一：可信状态基础

- 新鲜度、限时免费和 Channel 状态字段。
- 可回滚 Alembic 迁移和真实证据回填。
- 被动调用、主动探测写入统一验证语义。
- 前端区分“已验证”“待确认”“未验证”和“确认不可用”。

### 阶段二：三层探测

- 新模型入库基线探测。
- 长期无成功调用模型的低频心跳。
- 401/402/403/429 事件触发复检。
- 厂商级动态探测预算：取同一凭证可观测到的最小 RPD，心跳最多使用 1%，并至少为真实流量保留 90%；RPD 未知或小于 100 时跳过心跳。
- 连续 3 天无真实流量才进入心跳候选；同厂商串行探测，不同厂商全局最多并发 5 路。
- 事件复检使用统一 `check_run_id`，30 分钟内独立复检连续失败 3 次才确认策略变化；任一次恢复即终止批次。

### 阶段三：声明式厂商和扩容

- 使用 Pydantic 验证厂商 YAML。
- 先以 Mistral 的标准 OpenAI 兼容接口验证通用适配器；不接入需要绑卡的试用型厂商。
- 特殊认证、模型目录或免费判定继续使用自定义 Adapter。
- 候选池先生成 JSON/Markdown 报告和 YAML 草稿，不自动接入生产数据。

### 阶段四：个人代理策略

- API Key 保存厂商白/黑名单、RPM/RPD、最小上下文和默认偏好；个人版直接存于 Key 行，避免为一对一策略增加额外表。
- 请求级支持厂商排除、最小上下文、latency/capability 偏好和有序 fallback chain。
- 请求条件只能缩小可用范围，不能绕过全局安全规则。
- 路由保持确定性：健康度、新鲜度、用户偏好、延迟；429 后按顺序降级。
- 成功响应同时返回实际厂商/模型、是否 fallback 和最近验证时间。
- 增强现有 embedding/rerank，新增 image generation。

## 4. V1 验收目标

- 新模型入库后 1 分钟内完成真实基线验证。
- 从未成功调用的模型不会显示为“已验证”。
- 验证过期不会被误标为故障；确认失败不会被误标为待确认。
- Key 失效和单模型不可用在数据及界面上明确区分。
- 至少接入 8 家厂商，并重新核实每家的免费政策和使用条款。
- chat、embedding、rerank、image 各至少有一个已验证可调用模型。
- 保持单容器和 SQLite，无 Redis、无探测节点依赖。
